# Práctica 12.2 — Migración V4: tabla de categorías

## Enunciado

Crea el script `V4__crear_tabla_categoria.sql` que añada:

- Una tabla `categoria` con los campos `id` (PK autoincremento) y `nombre` (VARCHAR 100
  NOT NULL UNIQUE).
- Una columna `categoria_id` en la tabla `libro` como clave foránea opcional (nullable)
  que referencia a `categoria`.

No es necesario crear la entidad JPA en esta práctica; basta con el script SQL y verificar
en la consola H2.

## Solución

`src/main/resources/db/migration/V4__crear_tabla_categoria.sql`:

```sql
-- V4: tabla de categorías del catálogo. La entidad JPA Categoria (y
-- la relación @ManyToOne en Libro) queda fuera de esta práctica:
-- solo el esquema.

CREATE TABLE categoria (
    id     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL UNIQUE
);

ALTER TABLE libro ADD COLUMN categoria_id BIGINT REFERENCES categoria(id);
```

### Por qué `categoria_id` no lleva `NOT NULL`

El enunciado pide explícitamente una clave foránea "opcional (nullable)": a diferencia de
`usuario_id`/`libro_id` en la tabla `prestamo` (que sí llevan `NOT NULL` en `V1`, porque
un préstamo sin usuario o sin libro no tiene sentido), un libro del catálogo existente
—los que ya insertó `data.sql` antes de esta migración— no tiene todavía ninguna
categoría asignada. Si `categoria_id` llevara `NOT NULL`, la propia migración fallaría al
ejecutarse contra filas ya existentes en `libro` (todas tendrían `categoria_id = NULL` al
añadir la columna, violando la restricción de inmediato). Dejarla nullable permite que el
catálogo actual siga siendo válido sin categoría, y que se le asigne una más adelante
—precisamente el motivo por el que el enunciado no pide tampoco crear la entidad JPA
`Categoria` en esta práctica: primero el esquema, la relación en el modelo de dominio
puede llegar después, en otra migración.

### Por qué la sintaxis es la misma en H2 y PostgreSQL

Igual que `V1`/`V2`/`V3`, este script usa `GENERATED BY DEFAULT AS IDENTITY` (estándar
SQL, soportado por H2 2.x y PostgreSQL 16 por igual) en vez de `AUTO_INCREMENT` (MySQL) o
`SERIAL` (solo PostgreSQL) — el mismo criterio que ya documenta el comentario de cabecera
de `V1__crear_esquema.sql`, para que la migración no tenga que reescribirse al pasar de
`dev` (H2) a `prod` (PostgreSQL).

### Comprobación en la consola H2

```sql
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;
```

```
VERSION | DESCRIPTION              | SUCCESS
1       | crear esquema            | TRUE
2       | aniadir isbn a libro     | TRUE
3       | indice busqueda libro    | TRUE
4       | crear tabla categoria    | TRUE
```

```sql
SELECT column_name, is_nullable FROM information_schema.columns
WHERE table_name = 'LIBRO' AND column_name = 'CATEGORIA_ID';
```

```
COLUMN_NAME  | IS_NULLABLE
CATEGORIA_ID | YES
```

`IS_NULLABLE = YES` confirma que la columna quedó opcional, tal como pedía el enunciado.
